# Переход на HAProxy 3.4 LTS

Работа ведётся в alpha. Принятый интерфейс и все предшествующие исправления
перенесены в main коммитом `f731f5b`. Изменения перехода на 3.4 в это слияние
не входят. Смена ОС для первого этапа не требуется.

Первый этап проверен 6 ноября 2026 года: пакеты 3.4.7 с AWS-LC успешно
установлены в отдельных Ubuntu 24.04-средах AMD64 и ARM64. ARM64 проверялась
на dev с ограничением 1 CPU / 512 МиБ. На обеих архитектурах прошли проверки
Lua/ForwardAuth, TLS 1.2/1.3, Runtime API и повторной установки без изменений;
проверен также шаблон на пакетах 2.8. Отдельно бинарным файлом AWS-LC принят
реальный конфиг dev с условными настройками Lua/DH. Рабочие конфиг и процесс
dev на первом этапе не изменялись.

Второй этап завершён 6 ноября 2026 года. На dev ARM64 выполнен реальный переход
2.8.30 → 3.4.7 → 2.8.30 с проверкой отката, затем окончательный переход на
`3.4.7-0+ha34+ubuntu24.04u2`. Новый worker проверен по версии и SHA256 работающего
бинарного файла. Сохранены действующие баны, причины, счётчики и сроки
авторизации; при сравнении учитывается естественное истечение записей.
Исходный конфиг восстановлен побайтно. Контрольный маршрут панели, настоящая
Authelia и ответы семи настроенных HTTPS-адресов проверены до и после перехода.
guardd, controld, certd и Docker активны, временные peers и watchdog удалены,
ошибок незавершённых операций dpkg нет. Провайдер и ветка сохранены в root vars,
индекс APT обновлён; кандидат пакета совпадает с установленной 3.4.7.

В срезе до/после суммарная PSS master и worker выросла примерно с 14 до 32 МиБ.
Это наблюдение обычной работы, не нагрузочный тест; CPU и задержки под нагрузкой
предстоит сравнить в пункте 4. Постоянных дополнительных процессов миграция
не оставляет. Следующий этап — пункт 3, прежде всего обычные обновления 3.4.x.

Код второго этапа: `55cf2ee`. [Нативный CI ARM64/AMD64](https://github.com/CLLlAgOB/easy-ha-proxy/actions/runs/42227931943)
проверил пакет, Lua/TLS/Runtime API и установку/откат с настоящим systemd;
[общий CI](https://github.com/CLLlAgOB/easy-ha-proxy/actions/runs/42227931832)
проверил полный набор на Python 3.10–3.14, синтаксис, линтеры и секреты.

## Границы первого этапа

Целевая платформа: Ubuntu 24.04 noble, ARM64 (`aarch64` / `arm64`) и x64
(`x86_64` / `amd64`). Armbian с Ubuntu noble использует тот же ARM64-пакет;
это не расширяет гарантии поддержки ядра или оборудования Armbian.

Источник: подписанный community performance-репозиторий HAProxy Technologies,
ветка `ha34`. Пакет `haproxy-awslc` использует AWS-LC, заменяет обычный
`haproxy` и требует отдельной проверки TLS. Проверка контейнерной сборки с
OpenSSL не заменяет проверку этого пакета. Смена TLS-библиотеки относится
только к HAProxy, а не ко всем приложениям ОС.

По умолчанию сохраняется `haproxy_package_provider: distribution`.
Для отдельной тестовой системы без установленного HAProxy:

```yaml
haproxy_package_provider: haproxy-technologies
haproxy_package_branch: "3.4"
```

Это параметры установщика/Ansible, не веб-редактора конфигурации. Поддержка
других выпусков ОС добавляется после проверки их пакетов. Не подставлять
репозиторий noble на Ubuntu 22.04 или 26.04.

## 1. Источник пакетов и совместимость конфигурации

- Проверить наличие пакетов и зависимости отдельно для ARM64 и AMD64.
- Привязать ключ к отдельному `signed-by`, проверять его SHA-256; смена ключа
  требует явного пересмотра доверия. Не использовать глобальный `apt-key`.
- Ограничить пакет веткой 3.4; сторонний репозиторий не должен вытеснять
  одноимённые системные пакеты. Получать исправления 3.4.x без перехода на 3.5.
- Обычная установка/обновление должна отказывать при смене провайдера уже
  установленного HAProxy, включая случай потери настройки провайдера.
- Проверка состояния должна определять реальное имя установленного пакета.
- Выбирать режим boolean в Lua условием самого HAProxy `version_atleast(3.1)`,
  чтобы один шаблон оставался пригоден для 2.8 и 3.4, включая рендер из панели.
- Условием по признаку сборки `OPENSSL_AWSLC` исключать настройку DH, которую AWS-LC
  не поддерживает; для сборки с OpenSSL сохранять прежнее значение.
- Согласовать шаблон с проверкой в controld. Разрешать только два полных
  фиксированных блока совместимости; проверять их содержимое обычной политикой.
  Отклонять вложенность, другие условия, `.else`, незакрытые блоки и попытки
  спрятать снятие привилегий. Проверять принятие сгенерированного конфига
  службой управления до запуска самого HAProxy.
- Проверить реальную конфигурацию и Lua, успех/отказ/редирект авторизации,
  отказ при недоступности авторизации, TLS 1.2/1.3, Runtime API и парсер таблиц.
- Проверить повторную установку без изменений. CI должен выполнять проверку
  нативно на Ubuntu 24.04 AMD64 и ARM64.

Для одноразовой среды есть `.tests/integration/haproxy34-package.yml` и
`.tests/integration/haproxy_package_smoke.py`. Последний поднимает только
локальные временные слушатели и использует тестовый сервер ответов авторизации.
Это проверка Lua-контракта, а не полноценный вход в реальную Authelia.

На первом этапе рабочий пакет dev не заменяется: проверка выполняется в
изолированной среде. Новые лимиты HTTP/2, glitch-пороги, динамические backend
и малые буферы пока не включаются. Политика банов и исключения не меняются.

## 2. Управляемая миграция и откат на dev

Перед реализацией повторно проверить фактические версии, архитектуру,
источник APT и установленные зависимости. Не считать старый отчёт доказательством
текущего состояния. Перечитать maintainer scripts и systemd unit целевого пакета:
установка конфликтующего пакета может остановить старую службу.

Отдельная операция миграции должна:

1. Взять общий lock обслуживания, запретить параллельное применение конфигурации
   и проверить согласованность guardd/runtime/сохранённых банов.
2. Сохранить прежний deb-пакет, версии и необходимые deb-зависимости для
   автономного отката, конфигурацию, источник/приоритеты APT и systemd overrides.
   Секреты и сертификаты сохранять только на хосте с закрытыми правами.
3. Проверить новый бинарный файл с актуальной конфигурацией до переключения.
   Сохранить административное состояние backend и нужное состояние защиты;
   механизм server-state не сохраняет автоматически все stick-tables.
4. Выполнить контролируемое переключение. Проверить фактический бинарный файл
   работающего процесса, а не только `haproxy -v` на диске.
5. Проверить защищённые и открытые сайты, реальную Authelia, сокет и службы.
   При ошибке восстановить прежний согласованный набор пакетов, конфигурации
   и APT-настроек и повторить проверки доступности.
6. Воспроизвести отказ и откат на тестовой системе. Не считать наличие backup
   проверкой восстановления. Не обещать сохранение всех активных соединений.

До реализации и успешного испытания этой операции нельзя обходить запрет
смены провайдера обычным обновлением или вручную удалять пакет на рабочем dev.
Live-restore Docker не защищает от обновления самого HAProxy.

Операция реализована в `installer/haproxy_package_migrate.py`. Это отдельная
команда оператора с правами root; обычное обновление её не вызывает. Поддержаны
Ubuntu 24.04 ARM64 и AMD64 с дистрибутивным HAProxy 2.8, штатным unit и одним
локальным peer. Пользовательский unit, удалённые peers, неизвестная схема таблиц,
расхождение сохранённых решений guardd с runtime, незавершённая транзакция
конфига или параллельное обслуживание останавливают операцию до смены пакетов.
Нужны минимум 384 МиБ доступной RAM и 512 МиБ свободного диска.
После остановки службы управления файлы проверяются повторно: правка из панели,
успевшая завершиться во время начала обслуживания, сохраняется, а операция
отменяется до смены пакетов. То же правило действует для начала ручного отката.

Подготовка не меняет работающую службу и системные источники APT. Подпись
InRelease проверяется ключом с закреплённой контрольной суммой, а индексы и deb —
по цепочке SHA256. Точный старый пакет и новый набор сохраняются на самом хосте.
При переключении APT использует только закрытый локальный кеш, без загрузок
и без изменения посторонних пакетов. Обязательные отсутствующие библиотеки
libjemalloc2, libopentracing1 и libopentracing-c-wrapper0t64 заранее загружаются
через проверяемый APT Ubuntu и включаются в автономный кеш; при откате они тоже
удаляются. Уже установленные библиотеки не обновляются этой операцией.
Любая другая новая зависимость требует отдельной проверки и останавливает
подготовку. Временный policy-rc.d предотвращает
остановку HAProxy скриптами пакета; его прежнее содержимое восстанавливается.
На время конкретной установки и отката также задаётся NEEDRESTART_SUSPEND=1:
в Ubuntu 24.04 этот APT hook может вызывать systemctl независимо от policy-rc.d.
Постоянные настройки needrestart не меняются; HAProxy переключается явно.

Для `tbl_ban` и `tbl_ip_auth` временно запускается дополнительный HAProxy 2.8
без публичных слушателей. Он принимает таблицы по штатному peer-протоколу,
сохраняя причины, счётчики и оставшийся срок записей. Запись через `set table`
для восстановления не используется: она заново отсчитывала бы срок авторизации.
Снимок для сравнения хранится в SQLite, без загрузки всех записей в RAM Python.
Временный процесс ограничен 256 МиБ RAM и половиной ядра и удаляется после
проверенного завершения. Существующие лимиты запросов и исключения не меняются.

Выполняются проверки нового worker по версии и фактическому бинарному файлу,
таблиц, MAINT/весов backend, TLS с проверкой имени, контрольного маршрута панели,
анонимного доступа и здоровья настоящей Authelia. Внешний watchdog через пять
минут запускает восстановление, если команда оборвалась; завершённую операцию
он не отменяет. После трёх неудачных восстановлений требуется оператор.
Ошибки приложения после возобновления служб также вызывают откат. Недоступность
сети при заключительном обновлении индекса провайдера оставляет проверенный
HAProxy работающим и записывает предупреждение для повторного обновления APT.

Из каталога актуального исходного кода на хосте:

```sh
sudo python3 installer/haproxy_package_migrate.py prepare
sudo python3 installer/haproxy_package_migrate.py apply --id ID --exercise-rollback
# После успешной репетиции создать новую подготовку для окончательного перехода:
sudo python3 installer/haproxy_package_migrate.py prepare
sudo python3 installer/haproxy_package_migrate.py apply --id NEW_ID
sudo python3 installer/haproxy_package_migrate.py status --id NEW_ID
```

ID — 32 символа из ответа `prepare`. Подготовка действительна сутки и отменяется
при изменении управляемых файлов, пакетов или кода самой миграции. Копия команды
восстановления тоже проверяется по контрольной сумме. Журнал, пакеты и резервные копии
остаются в `/var/lib/easy-ha-proxy/haproxy-package-migration/ID` с закрытыми правами.
После успешного перехода провайдер и ветка сохраняются в vars.yml, а приоритеты
APT запрещают подмену пакета дистрибутивным или выход на другую ветку.
`rollback --id NEW_ID` возвращает 2.8 с актуальными таблицами, пока конфигурация,
переменные, версия и источники не изменились. После последующих правок нужна
новая квалификация отката. Для оборванной операции есть `recover --id ID`.

В изолированном AMD64 окружении проверены фактическая замена deb, reload,
принудительный откат после успешной проверки 3.4, восстановление после остановки
нового процесса и ручной откат после фиксации перехода. Причины банов, сроки,
авторизация, MAINT и вес backend сохранены. CI дополнительно выполняет эти
сценарии с настоящим systemd на нативных ARM64 и AMD64 runner.

Границы: peer не заменяет резервное питание или постоянное хранение всех
stick-tables. Одновременная потеря обоих процессов/хоста не покрыта этой
операцией. Первый обычный reload для подключения peer тоже требует исправного
старого HAProxy. Сохранение всех активных соединений не гарантируется.

## 3. Проверки поведения перед расширением функций

Подтверждён отдельный старый дефект для проверки Authelia: на дистрибутивном
2.8.30 с исходным шаблоном тестовый ForwardAuth вернул `200` и `Set-Cookie`,
но клиент получил `200` без этого cookie. Результат повторяется после исправления
порядка TCP/HTTP-правил; перестановка не является причиной. Проверить время жизни
`req.auth_response_header.set_cookie` при переходе к ответу, несколько cookie
и сохранение cookie самого приложения. Исправлять и квалифицировать отдельно;
текущая перестановка правил сохраняет прежнее поведение авторизации.

### Переход через веб-интерфейс

Исторический `override.conf` с фиксированным запуском
`/usr/sbin/haproxy -Ws -S /run/haproxy/master.sock,mode,660,user,root,group,haproxy -f /etc/haproxy/haproxy.cfg -p /run/haproxy.pid`
поддерживается отдельно: master-сокет и override сохраняются. Другие команды,
права master-сокета, смена пользователя или shell-обёртки по-прежнему требуют
отдельной проверки. Список и содержимое drop-in файлов фиксируются при
подготовке; их изменение до применения требует новой подготовки.

В alpha добавлена отдельная операция в **Обслуживание → Обновления → HAProxy →
Переход на HAProxy 3.4 LTS**. Для её появления нужно установить согласованную
сборку служб хоста и панели. Канал main/alpha выбирает версию проекта, а ветка
HAProxy меняется этой отдельной операцией.

1. Нажать «Проверить обновления». Карточка объясняет, если требуется обновить
   службы хоста, платформа не поддержана или HAProxy 3.4 уже установлен.
2. Нажать «Подготовить переход на 3.4». Фоновая задача проверяет настоящую
   конфигурацию и пакеты и загружает проверенный набор установки и отката.
   Работающая служба на этом шаге не переключается.
3. Проверить текущую и целевую версии, список пакетов и зависимостей. План
   по умолчанию действует 15 минут с момента завершения подготовки.
4. Ввести `MIGRATE 3.4` и нажать «Перейти на HAProxy 3.4 LTS». Применяется только
   этот подготовленный набор. Перед переключением повторяются проверки;
   изменение исходников миграции, конфигурации или пакетов требует подготовки
   заново. Возможны переподключения клиентов и панели.
5. Дождаться проверенного результата в карточке и журнале задания. После перехода
   выполнить новую проверку обновлений для актуальных версий пакета и worker.

Переход доступен только для квалифицированной Ubuntu 24.04 AMD64/ARM64 со
штатным HAProxy 2.8. Проверки нестандартных unit, peers, ресурсов и состояния
защиты остаются в существующем механизме миграции. Произвольные источники,
версии, команды и пути веб-клиент не передаёт. Переход не выбирается
автоматической установкой и не совмещается с другими компонентами обновления.

Задание и одноразовый план хранятся на хосте. Обновление страницы и временная
потеря связи не повторяют POST установки; интерфейс запрашивает состояние уже
принятой задачи. Откат после ошибки отображается отдельно от успешного перехода.
Непроверенное восстановление блокирует дальнейшее обслуживание. При необходимости
оператор использует сохранённую команду `recover.py`, описанную выше.

Подготовка и установка используют общий lock обслуживания; при передаче управления
от брокера root-процессу именно дочерняя операция удерживает lock до завершения.
Обычный план обновлений сбрасывается перед переключением; использованный план
миграции нельзя применить повторно.

### Управляемые обновления внутри ветки

В `/system/updates/` отдельная карточка HAProxy показывает пакет на диске,
версию фактического worker, доступный пакет, выбранную ветку/источник,
последнюю успешную проверку репозиториев и итог последней операции. Ошибка,
устаревшие индексы или расхождение бинарных файлов дают неизвестный либо
заблокированный статус; старое «обновлений нет» не является подтверждением.

Ручная и ежедневная проверка сначала обновляют подписанные индексы APT.
Это ограниченная по времени задача существующего брокера: максимум один CPU
и 512 MiB памяти, без установки пакетов и нового постоянного демона. Общая
блокировка обслуживания исключает пересечение с резервным копированием.

На квалифицированных Ubuntu 24.04 ARM64/AMD64 роль устанавливает `hold` для
HAProxy и его отдельной AWS-LC библиотеки. Обычный ha-install не обновляет уже
установленный vendor-пакет; системная и автоматическая установка обходят эти
пакеты. Для HAProxy отключён самостоятельный restart через needrestart;
заменённая системная библиотека отображается как необходимость управляемого
применения даже при неизменной версии HAProxy. Поэтому после системных
security-обновлений нужно выполнить предложенное применение библиотек.

Отдельная явная установка принимает только проверенную версию текущей ветки
2.8.x или 3.4.x. Перед переключением сохраняет точные старые deb, для 3.4 также
TLS-библиотеку, проверяет новый бинарный файл с настоящим конфигом и использует
тот же временный peer, снимок таблиц и независимый watchdog, что и миграция.
Сохраняются причины/TTL банов, авторизация, MAINT и веса серверов. При отказе
цели выполняется проверенный откат. Новая основная ветка — отдельная миграция.

Операторская команда внутри ветки:

```sh
sudo /opt/easy-ha-proxy/venv/bin/python /opt/easy-ha-proxy/source/installer/haproxy_package_migrate.py patch --expected-version VERSION
```

`--reinstall` нужен только для осознанного повторного применения той же версии.
Общая блокировка принадлежит дочерней операции вплоть до окончания переключения;
падение брокера не снимает её. Состояние и точный сохранённый `recover.py`
находятся в `/var/lib/easy-ha-proxy/haproxy-package-migration/ID/`.
Если восстановление требует оператора, другие операции обслуживания заблокированы;
сначала выполнить сохранённый `recover.py recover --id ID` и проверить журнал.
Текущий код из другого коммита не подменяет сохранённую команду восстановления.

В изолированном AMD64 окружении успешно проверены установка, автоматический
откат после остановки цели и ручной откат для обоих провайдеров. Подписанный
одноразовый тестовый репозиторий также меняет точную зависимость AWS-LC.
Это проверка механизма замены пакетов с реальными бинарными файлами, а не
квалификация ещё не выпущенного кода будущей версии. Нативный CI выполняет
те же сценарии с systemd на ARM64/AMD64. Проверка dev фиксируется отдельно.

Проверить отдельно: анонимный клиент, успешный вход, выход/истечение сессии,
администратор, глобальный и GEO белые списки, site allow_ips, TCP passthrough,
TLS к backend с проверкой имени, mTLS и отказ по недоверенному сертификату.
Убедиться, что контрольный запрос панели не позволяет обойти авторизацию извне.

Для u02 проверить обычное превышение и жёсткую атаку для каждого вида доверия,
начисление баллов guardd, ручной бан, истечение, снятие и восстановление после
reload/restart. Проверить CSV-метрики, Runtime API, вес и MAINT backend,
совместимость парсеров и загрузку таблиц. Ограниченный smoke первого этапа
не заменяет эти сценарии.

## 4. Измерения и новые функции

Сравнить 2.8 и 3.4 на одинаковых запросах и одинаковых лимитах CPU/RAM:
обычная работа, большой ответ, очередь медленного backend и контролируемый
поток атакующих запросов. Измерять RSS/PSS, CPU, ошибки, задержки обычных
клиентов и время применения команды бана. Нагрузку не подавать на рабочие сайты.

Включать по одному: малые буферы; ограничения параллелизма HTTP/2; сбор
протокольных аномалий; затем реакцию на подтверждённые аномалии. Для малой
системы нельзя просто копировать настройки для сотен тысяч соединений.
Доверенный IP не должен отключать защиту от разрушительной протокольной
нагрузки; единичная аномалия не должна автоматически становиться баном IP.
Объяснение причины должно попадать в события панели.

Динамические backend — отдельная доработка: определить сохранение изменений,
восстановление после restart, маршрутизацию и транзакционность. Наличие команды
в Runtime API само по себе не делает сохранение любого сайта работой без reload.

## 5. Распространение

После dev и CI провести проверку характерной конфигурации на x64. Проверка
пакета на чистом x64 runner не равнозначна проверке всех реальных сайтов.
Включать последовательно, сохраняя возможность отката. Переход ОС планировать
отдельно; поддержка Ubuntu не распространяется автоматически на сторонний пакет.
